# IoT设备网关验证报告

对应《伴月轩月子中心管理系统_软件项目开发计划_V1.0》P4阶段关键交付物"IoT设备网关框架 + 模拟设备接入验证报告"。本报告记录V1阶段用模拟设备验证"设备上报事件 → 业务事件转换 → 正式业务记录"链路的过程与结论。范围收窄的具体决策见 `docs/业务规则确认记录.md` 中"P4遗留IoT设备网关框架补齐"章节。

## 一、架构概述

- **不采购真实硬件，不搭建独立MQTT broker**：V1阶段作为`apps/api/src/iot/`模块跑在现有NestJS单体里，用HTTP接口模拟"设备上报"（`POST /iot/gateway/events`），代替真实网关的MQTT/CoAP接入层。未来真要接入真实硬件时，只需在这一层之前插入协议转换（MQTT broker → HTTP webhook），不影响已建好的事件转换与业务写入逻辑。
- **设备台账**（`Device`）+ **设备类型**（`DeviceType`，协议/品类主数据）+ **Device Shadow**（`DeviceShadow`，期望态desired/上报态reported分离存储）+ **事件流水**（`DeviceEvent`）+ **连接审计**（`DeviceConnectionLog`）五张表构成完整设备域模型。
- 7类设备（体征监测/安防看护/门禁出入/呼叫客房服务/身份结算/打印/能耗计量）均可登记台账、上报事件、被审计留痕；其中**呼叫/客房服务**与**能耗计量**两类接入了真实业务表的自动转换，其余5类本轮只留痕不转换。

## 二、验证方法

1. **后端集成测试**：`apps/api/test/p4-iot-flow.e2e-spec.ts`，8个用例，覆盖权限边界、呼叫事件成功/失败转换、能耗计量覆盖登记、无转换类别留痕、Device Shadow两步同步。全部通过，且与既有135个测试一起跑（共136个）不冲突（`--runInBand`下稳定通过两次）。
2. **浏览器真实点击验证**：在开发环境用超级管理员账号登录，通过导航菜单"设备网关"分组进入三个页面（设备类型/设备台账/事件与模拟），实际选择设备、触发模拟上报、下发/确认指令，确认页面展示与后端记录一致（细节见下表）。

## 三、验证结论

| 验证项 | 结果 |
|---|---|
| 呼叫/客房服务设备模拟上报（房间有在住占用） | 事件日志显示 `businessRefType: RoomCall`，跳转确认对应门店的呼叫记录列表中确实新增了该条记录，`reason`字段与上报载荷一致 |
| 呼叫/客房服务设备模拟上报（房间无在住占用） | 事件仍正常留痕（`processedAt`已写入），`processingError`记录"没有在住占用记录"，未抛500，不影响其他功能 |
| 能耗计量设备模拟上报（同门店同月份同类型二次上报） | 第二次上报后`UtilityExpense`金额被覆盖更新为最新值，未产生第二条记录（覆盖登记，不是流水叠加） |
| 其余类别（体征监测等）模拟上报 | 事件正常留痕，`businessRefType`为空，不触发任何业务表写入 |
| Device Shadow 指令下发 | 下发后`desiredVersion`+1，`reportedVersion`不变（尚未确认），期望态内容正确写入 |
| Device Shadow 模拟设备确认 | 确认后`reportedVersion`同步到与`desiredVersion`一致，上报态内容与期望态一致；重复确认（无待确认指令时）返回400 |
| 设备类型（总部主数据）权限边界 | 店长可查看（登记设备时需选择类型）但无法新建/修改；超级管理员不受限 |
| 设备台账权限边界 | 店长可自行新建/编辑本店设备（同房间/仓库口径） |
| 设备上下线状态 | 设备首次收到事件后自动从`OFFLINE`转为`ONLINE`并记录`lastSeenAt`，同时写入一条`ONLINE`连接审计日志 |

## 四、V1阶段暂不覆盖的部分（留待后续真实硬件接入时评估）

- 真实MQTT/CoAP网关接入、真实设备驱动适配器
- 体征监测/安防看护/门禁出入/身份结算/打印这5类设备与具体业务表的转换逻辑（本轮只做台账登记+事件留痕的架构预留）
- 门禁/监控等敏感设备指令下发的二次确认业务流程（`DeviceType.requiresCommandConfirmation`开关与Device Shadow两步同步机制已就绪，但尚无真实业务场景验证）
- 设备数据保留期限与访问权限分级（涉及体征/影像等敏感数据，需产品负责人后续明确）
