| 事项 | 处理方式 | 理由 |

| 库存成本核算方式 | WarehouseStock汇总层用移动加权平均法；StockBatch批次层只追踪数量与效期(供FEFO出库与过期预警)，不做批次级FIFO成本核算 | 竞品分析3.7明确"移动加权平均法核算成本"，批次级双轨核算(FIFO成本+加权平均汇总)复杂度过高，V1没有必要 |
| 服务物料桥梁(护理/产康服务核销自动生成待出库)、备料包(套餐→物料清单自动关联) | 本期不做 | 依赖P2已建的护理/产康/月子餐模块反向接入库存域，属于下一个切片的联动工作，不在"库存采购全流程"这一刀的范围内 |
| 月度结算锁账(按仓库逐月结算，结算后当月单据不可再新增) | 本期不做 | 依赖财务结算深化(#5待确认的结算优先级规则)一起设计，避免脱离财务模块单独做仓库锁账 |

| "会员账户/赠送优先"规则的落地载体 | 新建独立的 `CustomerAccount`(每客户一份，本金余额+赠送余额两个子池) + `CustomerAccountTransaction`(充值/消费/退款/调整四类流水，记录变动前后余额)，作为规则#5"赠送优先扣减"唯一的落地对象 | 竞品的"多资金池体系"(会员/套餐/续签/押金/服务卡各自独立核算)对V1过重；用一个账户的两个子池覆盖"赠送 vs 实付"这个核心区分，足以验证优先级规则，且不与已有 Payment(合同收款，强绑定 Contract)概念混淆——两者是不同性质的资金记录，不合并也不互相依赖 |
| 是否联动改造 CustomerServicePackage/ServiceAppointment 的核销选择逻辑 | 不改动，维持现状(前端/操作员显式指定 `sourcePackageId`) | 服务包对应不同项目类型，通常不能互相替代，"该消耗哪个包"更多是业务选择而非纯优先级问题；改造会牵动已完成并测试通过的P2产康服务模块，超出本次"结算优先级"任务范围 |
| 退款时如何在本金/赠送两个子池之间拆分 | 由操作员在退款时显式指定退回本金/赠送的具体金额，系统不做"反查原消费记录按比例自动拆分"的复杂关联 | 保持 API 简单直观；自动关联原消费流水反算比例需要额外设计"退款关联消费记录"的数据结构，收益有限 |
| 账户余额变更是否要求乐观锁 expectedVersion | 不要求，充值/消费/退款/调整均用数据库层面的原子 `increment` 保证并发安全，`version` 字段仅用于审计追溯，不做前端强制传入校验 | 账户余额是高频小额流水记账场景，不同于"整单编辑"的乐观锁语义；原子 increment 已能防止"丢失更新"，无需每次操作前多一次 GET |
| "人工调整"操作的权限级别 | 只开放给 SUPER_ADMIN，STORE_MANAGER 不可操作 | 调整脱离正常业务凭证、可任意改动余额，风险等级等同于"作废/标记流失"等既有的高风险操作，同一套收紧口径 |

| 事项 | 处理方式 | 理由 |
|---|---|---|
| 向量存储与检索方式 | 不引入独立向量数据库(pgvector/Milvus等)，复用现有MySQL：`KnowledgeChunk.embedding`存为JSON数组，检索时应用层(NestJS)取出该租户全部chunk做暴力余弦相似度计算，取top-K | 竞品分析与开发计划都把pgvector列为"起步阶段"选项之一；V1知识库文档量级(几十到上百篇文档)下暴力计算的性能完全够用，不必为此单独引入一套数据库基础设施；未来文档量显著增长再迁移到专用向量库 |
| 知识库内容来源 | 只做"手动创建知识库文档"通用入口(标题+正文+自由文本分类)，不自动从ContractTemplate/CareFormTemplate等业务表同步内容 | 自动同步需要额外设计"业务表内容变更时重新分段/重新embedding"的联动机制，超出本次范围；用户可以手动整理关键内容(如合同模板说明、护理规范摘要)录入知识库，符合开发计划里"导入首批业务文档"的最小化解读 |
| 分段(chunking)策略 | 按固定字符数(500字)切分，不做智能语义分段/重叠窗口 | V1文档量小，简单切分足够验证检索链路；语义分段收益在文档量大、内容结构复杂时才明显 |
| 两个Agent场景是否都接入知识库检索 | 都接入——智能客服与护理异常预警建议在生成前都会检索知识库并把命中片段加入prompt，复用同一套检索服务 | 开发文档里两个场景的"数据来源"栏都提到了知识库(智能客服:知识库RAG+客户历史；护理助手:护理知识库)，两者用同一套RAG基础设施成本很低 |
| Embedding与Chat用同一批模型供应商 | 是，复用已接入的火山引擎/MiniMax，在模型网关新增`/embeddings/create`接口，同样走供应商适配层+主备切换模式 | 避免引入第三方embedding专用服务，保持"两家境内合规供应商"这个既定边界 |
