## 已确认(2026-07-29 P3库存域启动，AI自行拍定的范围收窄——非用户逐条确认，供后续review)

| 事项 | 处理方式 | 理由 |
|---|---|---|
| 采购单是否受仓库"免审批"配置影响 | 不受影响，采购单始终走工作流审批 | 采购是花钱承诺，风险等级不同于仓内操作，即使仓库配置了免审批也不该跳过采购审批 |
| 挂在已审批采购单下的入库单是否需要再审批一次 | 跳过自身审批，直接视为已获授权 | 采购单审批时已经确认过"要不要买、买多少"，入库只是核实到货，避免同一件事重复走两次审批增加操作负担；未挂采购单的临时/盘盈类入库仍按仓库配置决定是否需要审批 |
| 调拨单（跨店）以哪一方仓库的"免审批"配置为准 | 以源仓库(fromWarehouse)配置为准 | 源头是承担库存流出风险的一方 |
| 采购数量与实际入库数量的超收/少收校验 | 不做强校验，只做展示对比 | 控制V1范围，实际业务中分批到货很常见，强校验容易造成误报拦阻正常收货 |
| 库存成本核算方式 | WarehouseStock汇总层用移动加权平均法；StockBatch批次层只追踪数量与效期(供FEFO出库与过期预警)，不做批次级FIFO成本核算 | 竞品分析3.7明确"移动加权平均法核算成本"，批次级双轨核算(FIFO成本+加权平均汇总)复杂度过高，V1没有必要 |
| 服务物料桥梁(护理/产康服务核销自动生成待出库)、备料包(套餐→物料清单自动关联) | 本期不做 | 依赖P2已建的护理/产康/月子餐模块反向接入库存域，属于下一个切片的联动工作，不在"库存采购全流程"这一刀的范围内 |
| 月度结算锁账(按仓库逐月结算，结算后当月单据不可再新增) | 本期不做 | 依赖财务结算深化(#5待确认的结算优先级规则)一起设计，避免脱离财务模块单独做仓库锁账 |

| 事项 | 处理方式 | 理由 |
|---|---|---|
| 员工档案是否新建独立实体 | 不新建，`EmployeeProfile` 作为 `Account` 的 1:1 HR 扩展表（accountId 唯一），只存 HR 特有字段（工号/入职日期/用工性质/健康证与合同到期日/转正日期/离职日期） | Account 已有 storeId/departmentId/teamId/positionId/姓名等身份信息，重开一套会造成两处数据源不一致 |
| 业绩提成(销售三级分账)与手工费(服务三人分摊) | 统一成一个 `CommissionRecord`(type=SALES\|LABOR) + `CommissionAllocation`(多条分配明细，角色用自由文本而非固定三级枚举) | 两者本质都是"一笔金额按比例分给多名员工"，用同一套模型覆盖，角色用自由文本比写死"销售/主管/店长"或"第一/第二/第三服务人"更灵活 |
| 业绩目标三级分配(门店→部门→员工月度目标 vs 实时/已审业绩三层对比) | 本期不做 | 属于经营分析范畴，且依赖尚未做的目标管理体系，V1先把"业绩记录本身能审批、能汇总进薪资"跑通 |
| 变更管理(退款/改单导致的提成冲正) | 本期不做自动联动，需要冲正时手工创建一条负金额的提成记录 | 呼应库存域"不允许物理删除只能冲正"的原则，但自动联动退款/改单事件依赖财务结算深化(#5)一起设计 |
| 薪资审批级数 | 固定2级(店长初审→超级管理员终审)，不是竞品的"最多3级" | 当前角色体系只有 SUPER_ADMIN/STORE_MANAGER 两个角色，凑3级会出现同一角色重复审批两次的无意义节点；2级已足以验证多级审批机制，后续人事组织结构细化后再加"财务审批"节点 |
| 排班班次(白班/中班/晚班/夜班/护士早班) | 做成门店级可配置的 `ShiftDefinition`(非写死的全局枚举)，`ScheduleEntry` 一人一天一条记录 | 不同门店的班次时段可能有差异；一天多班次(如拆分早晚班)本期不支持，需要时再拆 |
| 健康证/合同/转正到期提醒 | 只做数据字段+到期查询接口(仿库存过期预警模式)，不做自动推送通知 | 自动推送属于P4 AI/设备域"消息通知"范畴，本期先保证数据结构就绪 |
| 排班冲突检测、请假管理、自动排班建议 | 本期均不做 | V1只覆盖"手工登记排班"这一最小闭环 |

## 已确认(2026-07-29 P3财务结算深化实现中，AI自行拍定的范围收窄——非用户逐条确认，供后续review)

| 事项 | 处理方式 | 理由 |
|---|---|---|
| "会员账户/赠送优先"规则的落地载体 | 新建独立的 `CustomerAccount`(每客户一份，本金余额+赠送余额两个子池) + `CustomerAccountTransaction`(充值/消费/退款/调整四类流水，记录变动前后余额)，作为规则#5"赠送优先扣减"唯一的落地对象 | 竞品的"多资金池体系"(会员/套餐/续签/押金/服务卡各自独立核算)对V1过重；用一个账户的两个子池覆盖"赠送 vs 实付"这个核心区分，足以验证优先级规则，且不与已有 Payment(合同收款，强绑定 Contract)概念混淆——两者是不同性质的资金记录，不合并也不互相依赖 |
| 是否联动改造 CustomerServicePackage/ServiceAppointment 的核销选择逻辑 | 不改动，维持现状(前端/操作员显式指定 `sourcePackageId`) | 服务包对应不同项目类型，通常不能互相替代，"该消耗哪个包"更多是业务选择而非纯优先级问题；改造会牵动已完成并测试通过的P2产康服务模块，超出本次"结算优先级"任务范围 |
| 退款时如何在本金/赠送两个子池之间拆分 | 由操作员在退款时显式指定退回本金/赠送的具体金额，系统不做"反查原消费记录按比例自动拆分"的复杂关联 | 保持 API 简单直观；自动关联原消费流水反算比例需要额外设计"退款关联消费记录"的数据结构，收益有限 |
| 账户余额变更是否要求乐观锁 expectedVersion | 不要求，充值/消费/退款/调整均用数据库层面的原子 `increment` 保证并发安全，`version` 字段仅用于审计追溯，不做前端强制传入校验 | 账户余额是高频小额流水记账场景，不同于"整单编辑"的乐观锁语义；原子 increment 已能防止"丢失更新"，无需每次操作前多一次 GET |
| "人工调整"操作的权限级别 | 只开放给 SUPER_ADMIN，STORE_MANAGER 不可操作 | 调整脱离正常业务凭证、可任意改动余额，风险等级等同于"作废/标记流失"等既有的高风险操作，同一套收紧口径 |
