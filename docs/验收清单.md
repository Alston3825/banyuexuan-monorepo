## 测试策略核查（计划书第3.3节，本轮搭建CI时才发现）

计划书3.3节明确要求两类测试**分别**满足："状态机与金额计算类逻辑（合同结算、退款、库存扣减、提成计算）必须有单元测试覆盖，这是资金安全的最后防线"+"核心闭环需要端到端集成测试"。

| 验收项 | 结论 |
|---|---|
| 端到端集成测试 | ✅已完成，162个e2e用例覆盖P1-P5全部核心闭环 |
| e2e测试套件对"新鲜数据库"的可复现性 | ✅**本轮搭CI时发现并已修复**：`test_user`账号（7个e2e测试文件依赖它验证跨门店越权场景）此前从未写进`seed.ts`，只是碰巧一直存在于长期未重置的共享开发库里——用一个全新的空数据库实测（`prisma migrate deploy`+`prisma db seed`+跑全部162个e2e用例），79个测试直接401失败。已在`seed.ts`里补上`test_user`+第二家门店+对应角色授权（放在非生产环境的示例数据区块里），修复后全新数据库上162/162全部通过。这类"测试套件偷偷依赖手工攒出来的共享数据库状态"的问题，如果不是这次专门用全新数据库跑一遍，不会被发现——CI流水线以后每次都是全新库，这类问题以后会在合并前直接暴露，不会再悄悄潜伏。 |
| 状态机/金额计算类逻辑的单元测试 | ❌**【缺口，本轮搭CI时才发现】** 全仓库搜索`*.spec.ts`（`apps/api/package.json`里`test`脚本运行的正是这个匹配规则），**一个单元测试文件都没有**，`npm run test --workspace=@banyuexuan/api`直接报"No tests found"退出码1。这意味着计划书特别点名"资金安全的最后防线"这一条实际上完全没有落地——现在合同结算、退款、库存扣减、提成计算这些金额逻辑的正确性完全依赖e2e测试间接覆盖，没有针对具体计算函数的单元测试。这是一个比其他缺口更值得优先处理的技术债，已经单独开一个后台任务跟进（`清理apps/api的66条历史ESLint报错`是另一条，这条是测试覆盖，两者都建议尽快安排）。 |

## 汇总

- **P0-P4的核心业务功能验收项**：全部✅或属于"按计划确认过的主动收窄"，没有意料之外的功能缺口。
- **真正需要本轮"上线准备"补齐的缺口**（都是运维/工程基础设施类，不是业务功能）：
  1. CI/CD 从未搭建（P0遗留）
  2. 应用本身没有Dockerfile/生产容器化（Docker Compose目前只跑dev的MySQL/Redis）
  3. 预发/生产环境从未真正搭建过
  4. 四份计划书要求的"手册"类文档均未写：环境与密钥管理手册（P0）、合同/网签模板配置手册（P1）、审批流程配置手册（P3）、AI治理与人工复核规则手册（P4）
  5. 生产环境安全基线未核查：CORS当前完全未开启、无helmet安全头、无接口限流、Swagger文档`/api/v1/docs`默认暴露无环境隔离
  6. 审计日志时间区间筛选未打通（小缺口）
  7. 状态机/金额计算类逻辑完全没有单元测试（零`*.spec.ts`文件），只靠e2e间接覆盖（本轮搭CI时才发现，已开后台任务跟进）
  8. apps/api有66条历史遗留ESLint报错，从未作为强制门槛跑过（本轮搭CI时才发现，已开后台任务跟进）
- **上线之后才能做的事**：真实API Key端到端冒烟测试、真正的P95性能统计（需要真实流量+APM）。
- **明确不做、已有结论的事**：商城V1、会员等级/积分、跨店结算优先级、MCP工具协议、完整合规电子签章。
