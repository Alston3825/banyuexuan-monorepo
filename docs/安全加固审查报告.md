# 安全加固审查报告

对应《伴月轩月子中心管理系统_软件项目开发计划_V1.0》P5阶段"性能安全+PWA+真实硬件"任务里的安全加固部分。

## 审查方法

用`security-review`技能对`claude/postpartum-center-software-architecture-1aa44f`分支相对`main`的全部新增代码做了一轮定向安全审查（覆盖P2-P5新建的全部业务模块）。子agent识别出候选问题后，逐条重新读取源码原文人工核实，只保留确认属实、置信度≥8/10的发现。

## 核心发现：三个新模块系统性遗漏了门店范围校验

审查发现IoT设备网关、培训考核、离店后关怀跟踪这三个P4/P5新建模块，存在同一类模式的越权问题：**"待办列表不做门店过滤 + 按id操作不做归属校验"**。具体表现为两种组合：

1. **列表接口泄露跨门店数据**：只用`tenantId`过滤查询条件，没有用已有的`DataScopeService`把结果收紧到调用方自己的门店范围，导致店长能看到其他门店的数据（设备台账、待批阅考试、待跟进客户关怀任务及其PII）。
2. **按id操作的接口没有校验目标记录的门店归属**：只要能拿到一个id（往往就是通过上面第1点的列表泄露拿到的，不需要猜测），就能对其他门店的记录做写操作（批改考试成绩、标记关怀任务完成、终止关怀计划、下发设备指令）。

这两点组合起来，构成了完整的"先枚举、再篡改"攻击链。同一分支里`business-report.service.ts`、`crm/customer.service.ts`等模块已经正确使用`DataScopeService`做了这件事，说明不是不知道这个约定，只是三个新模块在写的时候漏掉了。

## 已修复的问题清单

| 模块 | 文件 | 问题 | 修复方式 |
|---|---|---|---|
| IoT设备网关 | `iot/device-gateway/device-gateway.service.ts` | 呼叫事件按房间号查占用记录时未限定门店，异店设备可伪造呼叫记录 | 查询条件加`storeId: device.storeId` |
| IoT设备网关 | `iot/device/device.service.ts` | 设备台账列表只按租户过滤，可看到其他门店全部设备 | 用`DataScopeService`收紧到调用方门店范围 |
| IoT设备网关 | `iot/device-gateway/device-gateway.service.ts` | 设备查找/事件日志/指令下发/确认全都没做门店（部分连租户都没做）校验 | 统一加`tenantId`过滤 + `assertStoreAccessible`门店校验 |
| 培训考核 | `training/exam-attempt/exam-attempt.service.ts` | 待批阅列表跨门店可见；批阅接口可跨门店篡改他人考试成绩 | 待批阅列表按员工所属门店收紧；批阅前校验作答人门店归属 |
| 离店后关怀 | `care/care-outreach-plan/care-outreach-plan.service.ts` | 待跟进任务列表跨门店泄露客户信息；完成/终止接口可跨门店篡改 | 列表按门店收紧；完成任务/终止计划前都校验门店归属 |

具体改动见对应文件，修复方式统一复用已有的`DataScopeService.resolveAllowedStoreIds()` / `assertStoreAccessible()`，没有引入新的授权机制。

## 回归测试

在三个模块各自的e2e测试文件里补充了跨门店越权场景（用`store_manager`与`test_user`两个绑定不同门店的账号互相验证）：
- `apps/api/test/p4-iot-flow.e2e-spec.ts`：设备列表门店隔离、Shadow跨店操作被拒绝、跨店呼叫事件注入被拦截（3用例）
- `apps/api/test/p5-training-exam-flow.e2e-spec.ts`：待批阅列表门店隔离 + 跨店批阅被拒绝（1用例）
- `apps/api/test/p5-care-outreach-flow.e2e-spec.ts`：待跟进列表门店隔离 + 跨店完成任务/终止计划被拒绝（1用例）

全量162个e2e测试通过（原157个+新增5个），前后端build均无误。

## 未处理事项（供后续review）

审查中还发现一条置信度7/10（低于本轮8分筛选门槛）的问题：`Device`表的`findOneOrThrow`/`update`（继承自`BaseScopedCrudService`）本身不做任何门店范围校验，理论上如果能猜中另一个门店的设备cuid就能读写——但这是全项目所有基于`BaseScopedCrudService`的模块共用的基类行为（几十个模块都是这个模式），不是这几个新模块独有的问题，且此项目一贯把cuid视为不可猜测（已有多处这个假设）。是否要给基类整体加门店范围校验，属于更大范围的架构决策，不在本轮"三个新模块"的修复范围内，留给后续单独评估。
