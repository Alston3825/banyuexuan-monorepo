# 真实硬件设备接入评估报告

对应《伴月轩月子中心管理系统_软件项目开发计划_V1.0》P5阶段"性能安全+PWA+真实硬件"任务里的真实硬件部分。这是一份研究性评估，不涉及实际采购或代码改动——V1阶段本来就明确"不采购具体硬件，只预留接入能力"（见《新系统开发文档》3.4节），这份报告是在那个决策基础上，回答"如果以后真要接，大概要做什么、先接哪个"。

## 现状：架构已经准备好了，缺的是"真实设备"这一端

P4遗留补齐阶段已经搭建了完整的设备网关框架（`apps/api/src/iot/`）：设备类型/设备台账两层主数据、Device Shadow（期望态/上报态分离）、事件流水、连接审计，并且用"模拟设备事件"验证过"上报→业务记录自动生成"这条链路是通的（呼叫服务→RoomCall，能耗计量→UtilityExpense）。

这意味着**接入真实硬件不需要改动核心业务逻辑**——需要新增的只是"设备→我们的HTTP接口"这一段真实的数据管道，替换掉现在前端"模拟设备事件"面板手工点击触发的部分。这正是当初设计Device Shadow模型时特意做的解耦。

## 分设备类别评估：接入真实硬件大概要做什么

开发文档列了7类设备，本轮IoT框架验证时选了"呼叫/客房服务"和"能耗计量"两类接了真实业务表。逐类看接入真实硬件还缺什么：

| 设备类别 | 协议 | 还缺什么才能接真实设备 | 复杂度 |
|---|---|---|---|
| 呼叫与客房服务 | MQTT | 业务转换逻辑已就绪；缺一个真实的MQTT broker（如EMQX）+ 从broker订阅消息转发到`/iot/gateway/events`的桥接程序（几十行代码），以及采购呼叫器硬件本身 | 低——链路最短，建议优先 |
| 能耗计量 | MQTT / RS485转网关 | 同上需要MQTT broker+桥接；另外真实智能水电表通常自带RS485转MQTT的网关设备，需要按具体表具型号对接其私有协议字段（不同厂商表具的数据格式不统一，这部分工作量因厂商而异，需要选定具体型号后才能估算） | 中——协议桥接工作量取决于具体表具品牌 |
| 体征监测 | MQTT / BLE网关上报 | 业务转换逻辑本轮**没做**（只留痕不生成护理记录），需要先补上"设备上报→写入CareRecord"的转换逻辑，且这类数据涉及护理判断，写入前该不该要求人工确认需要重新拿到业务规则确认——不是纯技术工作 | 高——涉及护理业务规则，不只是技术对接 |
| 安防与看护 | RTSP/MQTT事件上报 | 视频流(RTSP)接入是全新的技术栈（本系统目前不处理任何音视频流），且涉及监控录像的存储、隐私合规、留存期限等，超出现有IoT网关框架的设计范围 | 高——需要独立的技术方案，不是现有框架能简单扩展的 |
| 门禁与出入 | MQTT/Wiegand网关 | 业务转换逻辑本轮没做；且门禁属于"敏感设备"，指令下发需要二次确认（Device Shadow框架已预留这个开关，但没有具体业务场景验证过） | 中高——需要先定义门禁场景的具体业务规则 |
| 身份与结算 | 串口/USB网关转HTTP | 与其说是"IoT设备"，更像是"外设驱动"（读卡器插在收银电脑上，走本地API而非网络协议），接入方式和现有MQTT网关框架不是同一类技术，需要单独设计 | 中——技术路径与其他6类不同 |
| 打印 | 局域网打印协议 | 同上，是打印驱动集成问题，不是IoT设备网关要解决的问题 | 中——技术路径不同，不适合套用现有框架 |

## 建议

1. **不建议现在采购任何硬件**——本报告确认了架构已就绪、成本主要在"选型+协议桥接+可能的定制开发"，但目前没有具体的品牌/型号，无法给出真实的采购清单和预算，采购决策应该等到有具体的业务驱动（比如某个门店明确想解决"人工抄表耗时"这类具体痛点）时再启动。
2. 如果未来要试点，"呼叫与客房服务"是技术路径最短的一类——协议最简单（纯MQTT）、业务转换逻辑已经验证过、且能直接替代现有的人工按铃登记，建议作为第一个试点对象。
3. "体征监测"和"安防与看护"涉及护理判断或全新技术栈（音视频），即使确定要做，也应该分别当作独立的评估/开发任务来对待，不能简单套用现有IoT网关框架的开发节奏来估算工作量。
4. "身份与结算"和"打印"严格来说不是"IoT设备"，是外设驱动集成，技术路径完全不同，不建议放在同一个"IoT设备接入"计划里一起推进。
