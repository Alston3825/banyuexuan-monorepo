## 一、产品定位总览

一月妈咪是一套面向**连锁月子中心**的 SaaS 后台管理系统,组织架构为"集团(会宝云服)→区域→门店→部门/职务/团队"四到五级,系统信息页显示按"门店数/账户数/房间数"分级授权(如"最大授权门店数10+0""最大授权账户数10000"),证实是按规模分级收费的订阅制产品。

顶部一级导航固定为 **11 个模块**(另有商城、知识库通过"更多"入口挂载,系统模块归口):
**客户 / 房间 / 护理 / 服务 / 办公 / 财务 / 人事 / 统计 / 月嫂 / 系统 / 更多(商城、月子餐、库存、知识库等)**。

系统整体呈现三个鲜明的架构特征,建议作为"伴月轩"自研系统的重点参考:

1. **统一"服务单"数据模型**:产康服务、零售商品、客户点餐三类业务共用同一套"产品目录(设置-产品管理)→购买(选客户→下单→销售单)→排期(服务计划/技师预约)→执行(今日服务/今日商品/今日点餐三个Tab)→核销(确认完成+物料出库)"框架,极大减少了重复造轮子。
2. **可配置化表单/审批引擎**:护理表单(护理字段管理→护理项目管理→护理方案管理→档案模板管理四层)、审批流程(审批项目自定义类型/层级/审批人/是否联动生成采购单·出库单·支出单)均做成了元数据驱动的可配置引擎,而非硬编码。
3. **RBAC + 多门店双维度权限**:角色 = 功能权限矩阵(约20个业务大类、数百个功能点,分"业务操作权限"与"基础设置权限"两栏,并对高风险/特权操作做"‑危""‑特"标注) × 应用门店范围,门店级别还能对具体功能做插拔式开关(见"系统"模块)。

## 三、各模块详细功能与关键业务规则

> 以下按模块给出:核心定位、关键页面/字段要点、值得借鉴的业务规则。完整逐页细节见分析过程产出的原始笔记(如需可另附)。

### 3.1 客户(CRM)—— 系统的销售中枢

- **公海/私海机制**:客户分"有归属(私海)"与"公海"两态,按"未跟进天数"分级(近20天未新客户 / 20天未签约 / 7天未跟进…);跟进级别 A(非常有意向)/B/C/D 四级打分。放弃客户需走"无效客户审核",防止销售私自洗客户/藏线索。
- **多门店"同城共享"**:连锁门店间可共享/争抢彼此的公海客户与无效客户资源池。
- **销售角色三分离**:电话销售 / 门店销售 / 签约销售分别记录归属,便于分环节提成核算(与人事模块提成体系对应)。
- **线索三通道**:客户预约(小程序到店预约)、询价记录(在线问卷询价)、其他线索(活动/转介绍/地推人工录入),统一汇入客户池。
- **销售机会(Opportunity)独立于客户**:一对多关系,支持跨产品线(月子房/月嫂/产康/托育/月子餐)交叉销售商机追踪,状态机:跟进中→已成单/已取消。
- **双合同体系并行**:传统 Word 合同(变量占位符模板生成) + 网签电子合同。网签合同状态机:**制单中→审批中→(未通过/待签约)→已签约**,异常分支:作废/拒签/合同过期/合同异常/已撤回;审批人可配置第一/第二/第三级(逐级可修改下一审批人)。
- **强内控审批**:新签约需"客户签约审核"通过才生效;敏感字段(手机号)变更、签约备注变更均留痕审计。
- **超级会员(SVIP)体系**:多档等级(月/年/3年/5年阶梯定价),每档可单独配置商品/服务包/套餐的专属折扣或免费权益,配套会员日志(含折算余额、升级退款等复杂换算)。
- **问卷五段闭环**:问卷管理(模板库+二维码分发)→问卷计划(按客户批量分配、设定周期)→问卷记录(得分)→问卷统计(完成率)→问卷分析(题目/分类交叉平均分,可下钻到管家维度)。
- **投诉/服务爆点双轨**:投诉建议(负向)与服务爆点(正向亮点)并行记录,均按房间/客户强绑定;重大问题可越级至"院长信箱"(48小时内可修改处理说明,超时锁定)。
- **画像管理=自定义字段引擎**:后台可自由增加"用户画像"字段(单选/多选/字符/日期/货币等类型),并配置是否进列表、是否进图表分析——是系统"可配置化"设计思路的典型代表。
- ⚠️ **隐私风险提示**:客户标签/画像含"企业高管""明星""官员家属""军人家属"等敏感身份标识,自建系统需评估是否保留此类分层,若保留需加强访问控制与合规审查。

### 3.2 房间(酒店式 PMS)

- **五种房态视图**并存,服务不同角色:看板卡片(前台日常)、精简楼层视图(客服高频操作)、按月甘特图(中长期排房规划)、横排/竖排两种转置视图(排查空档/冲突,"重"字标红提示重叠预订)、深色大屏客户呼叫看板(夜间值班)。
- **房态分析六件套**支撑经营决策:房型分析表(入住率/预订率/使用率/空置率四指标)、预订量分析(逐日趋势折线图)、入住率对比(多门店横向)、空置率分析(逐月热力标记)、**房间销控表**(未来近一年甘特图,签约时判断可售房源)、**客户排房表**(已签约未排房提醒清单,是 CRM 签约→排房的关键衔接页)。
- **出入日历**:月历双维度统计(房间空/预/用/留 + 客户入/离/在/邀约),配套逐日客户名单列表,供财务对账/运营日报使用。
- **呼叫系统**:呼叫内容字典(宝宝喂奶/换尿布/打扫房间…)→呼叫记录(工单,未处理红字)→客户呼叫大屏看板可视化。
- **外出管理**:登记妈妈/宝宝离所原因,系统按预设"风险模板"自动附加安全告知文案,做安全责任留痕。
- **客房服务(物品领用)**:领用包模板(常用物品组合)+领用记录(含赔偿金额字段),对接资产/押金结算。

### 3.3 护理(母婴健康档案 + 执行 + 质控)

这是系统**技术含量最高**的模块,建议重点参考其"表单引擎"设计:

- **四层可配置表单引擎**:护理字段管理(字段元数据:控件类型/选项/正常值域/是否客户端可见)→护理项目管理(表单模板容器,按部门:护理部/产康部/膳食部/客服部/医务部;按场景:通用/所内/上户/医院)→护理方案管理(多表单组合成"天数化方案",如"妈妈护理入住方案28天")→档案模板管理(入住/离店评估表模板)。四层组合支撑"护理计划"自动按入住天数排出每日任务卡片。
- **母婴双档案线**:每个客户拆成"妈妈"与"宝宝"两条并行档案(支持多胞胎切换),日常护理表单字段极其详尽——
  - 妈妈:班次、乳头、乳汁(未泌/已泌)、恶露(量/色/情况)、伤口情况、子宫、水肿、排泄、体温、心率、宫底高度、腹直肌分离(公分)等;
  - 宝宝:排便/排尿次数、喂奶(ml)、黄疸(mg/dl)、大便性质、Apgar评分、拥抱反射等专业指标。
- **护理异常自动预警**:系统按"护理字段管理"预设的正常值域自动比对填写值,超范围即标红计入"护理异常"列表,支持指定通知人订阅、处理闭环。
- **孕周提醒**:按预产期自动倒推孕周,每周推送知识文案,覆盖未入住的意向客户,是孕期潜客维系工具。
- **颜色标签体系**:早产/宝宝住院/一对一/宝宝托管/传染病/高敏/妈咪住院,贯穿房态、护理、客户等多个列表页的风险可视化。

### 3.4 服务(产康/商品/点餐交易与执行)

- **统一"服务单"模型**:产康、零售商品、客户点餐三类业务共享同一套"产品目录→购买下单→排期(服务计划/技师预约)→今日执行(今日服务/今日商品/今日点餐)→确认完成+物料出库"框架。
- **产品设置双向绑定**:每个产品(服务/商品/点餐/膳品)在设置中预绑定"默认物料",购买/核销后自动触发库存出库,是服务模块打通库存的关键设计。
- **技师排班双视图**:技师预约A(团队×时段块状视图)与技师预约B(全天精细时间表),供不同排班习惯的人员使用。
- **优惠审批**:折扣超出员工权限自动拦截并生成"优惠申请",支持有权限用户越级代批。
- **服务包两级定价**:按项目定价(子项累加) vs 打包总定价(一口价),且可标记"可用于套餐"(作为整体入住套餐赠送内容)。
- **按需项目机制**:服务包购买时不预先绑定具体项目(如"35次任选服务包"),执行时才临时"创建项目"消耗额度,受总次数/单项上限约束。
- **客户分析五件套**:消费分析(购买视角)、服务分析(完成视角)、服务反馈分析(满意度评分+文字评价)、沉睡客户分析(按最后购买/服务时间自动计算沉睡天数)、客户回访管理(按"产后第X月""离店后第X月"自动圈定回访节点,是产后关怀CRM的核心)。
- **跨店服务通兑**:客户在A店购买、B店执行,系统同时生成"执行记录"(执行门店视角)与"消项记录"(销售门店视角)互为镜像,支撑连锁总部结算。
- **双销售人分成**:销售单/服务包购买均支持"主销售+次销售"两人分账,对接人事模块提成计算。

### 3.5 月嫂(住家护理人力资源撮合)

- 本质是嵌入式的"HR + 订单撮合 + 薪酬结算"子系统,业务闭环:**预约申请→面试管理→派单记录→档期管理→上单/结算**。
- 月嫂档案信息极丰富(背调、健康证、保险、性格测试、犯罪记录、传染病筛查等),体现住家型人员的强合规要求。
- **档期查询/档期日历**:横向时间轴 + 矩阵日历双视图,支撑派单人员快速找空档并"一键派单"。
- **核心薪酬公式**(直接写在页面说明中,极具参考价值):
  - 期间上单天数 = 上单天数 + 期间增减天数
  - 薪资预算 = 派单日薪 ×(派单天数+增减天数)+ 增减薪酬
  - 派单节省 = 期望日薪 ×(派单天数+增减天数)− 派单日薪 ×(派单天数+增减天数)+ 增减薪资
  - 备注:上单按夜统计,休假按天统计
- 月嫂等级(星级/金牌/高级等)与标签(线上/线下、员工制/非员工制、黑名单)双轨分类,兼顾定价档次与风控。
- 月嫂档案可生成对外分享链接/海报,支持"月嫂列表客户端"H5公开页面,供客户浏览挑选——即前台"选月嫂"功能。

### 3.6 月子餐(膳食计划管理)

- **计划类型覆盖多场景**:月子餐计划/小月子计划/试吃计划/外送餐计划/VIP排餐,均可配置"阶段化天数"(如"7‑7‑7‑7"即28天分4个7天阶段,对应产褥期分阶段营养需求)。
- **排餐三级结构**:膳食计划(模板)→用膳人管理(客户逐个绑定计划,含开始/截止餐次)→月子餐排餐表(按阶段+餐次汇总展示,支持批量"初始化用餐")。
- **自选餐机制**:客户可在系统提供选项内自主选餐,但受严格规则约束(当日9点前确认、早餐/早点不可当日选、确认后覆盖默认排餐、以"每日排餐"实际结果为准)。
- **预算→采购/出库联动**(与库存模块打通的关键证据):菜品预算(汇总当日各餐次份数与配方)→食材预算(折算为具体食材用量,对比当前库存,**一键"生成采购单"或"生成出库单"**)。
- **禁忌体系双轨**:食材类禁忌(忌鸡蛋/忌牛肉等)+ 病理性禁忌(妊娠高血压/妊娠糖尿病等),与护理模块的"医嘱""过敏史"字段潜在联动。

### 3.7 库存(进销存全链路)

- **单据体系统一走"制单→审批→执行→出入库明细→月结算锁账"**:采购单(CG)→入库单(RK)→出库单(CK)→调拨单(DB,含跨店)→领用单(LY)→盘点单(PD),移动加权平均法核算成本。
- **服务物料是关键桥梁**:护理/产康服务项目预设物料消耗清单,服务核销后自动生成"待出库"列表,可精确追溯到"来源客户+来源项目+销售单号",支撑单项服务成本核算。
- **备料包="套餐即物料清单"**:客户签约套餐后自动关联备料包模板(如"28天套餐备料包"),按客户/房间维度跟踪送达+出库两条独立状态线。
- **月度结算锁账**:按仓库逐月结算,结算后当月单据不可再新增,与财务成本核算周期对应。
- **效期/预警双机制**:库存预警(低于阈值提醒补货)+ 过期预警(按保质期天数提醒,防止过期食材/耗材使用)。
- **多门店/多仓库架构**:每门店可建多仓库,支持仓库级"免审批"配置及"跨店调拨"。

### 3.8 财务(账务与资金枢纽)

- **预收款分期确认收入**(权责发生制):套餐结算/续签结算按"入住夜数"逐日把预收款转为已确认收入。计算公式:
  - 当前夜均费用 =(签约/续签金额 − 已结算金额)÷(结束时间 − 已结算时间)
  - 待结算金额 = 当前夜均费用 × 待结算天数;离店当天不计入当夜结算。
- **成本管理(签约利润表)**:每份合同的收入与摊派成本(月嫂/房间/物料/人员/运营/膳食/其他)逐单对比算出利润率,是定价与套餐设计的决策依据。
- **多资金池账户体系**:会员账户/套餐账户/续签账户/押金账户/服务卡账户(充值+赠送两个子池)/代金卡,彼此独立核算,期初期末余额可勾稽核对。
- **服务卡 vs 代金卡**:服务卡绑定已知客户(会员权益属性),代金卡支持匿名批量制卡+后续实名激活+挂失(类似商场购物卡,适合渠道分销/员工福利)。
- **资金管理四层架构**:业务收付款(销售/服务卡/采购等产生原始记录)→收款入账/付款出账(确认归属资金账户,自动计提手续费)→账户资金(实时余额看板)→出入账查询(全量流水+复核机制)。支持"6个月对冲权限"做差错红冲。
- **收款管理是前台窗口**:客户收款‑财务管理页汇总四类账户(会员/套餐/续签/押金)+服务卡账户,统一发起收款/退款/开票/打印结算单,是单客户视角的一站式财务工作台。
- **统计报表体系**:应收/应付汇总、预期收款(未来3个月现金流预测)、日结统计(收银员签字对账单)、财务统计(期初‑本期变动‑期末模型)。

### 3.9 人事(人力资源与薪酬中枢)

- **双提成体系并行**:业绩提成(基于签约/续签/服务包/项目/服务卡等"回款"触发,业绩提成指数管理支持销售/主管/店长三级分层分账)+ **手工费**(基于护理/产康具体服务项目,第一/第二/第三服务人分摊,与业绩提成体系独立并行)。
- **业绩全生命周期**:业绩申请→业绩审批→(变更管理处理退款/改单冲正)→业绩查询/统计→奖金统计,支持一笔业绩按比例拆分给多名员工。
- **薪资三级审批**:薪资模板(按部门/岗位预建结构)→薪资单制单→最多3级审批(可驳回→重新制单→再提交,操作日志全留痕)→薪资明细/工资条。
- **业绩目标三级分配**:门店→部门→员工逐层设置月度目标(需分配比例达100%),配套"目标 vs 实时业绩 vs 已审核业绩"三层对比分析。
- **健康证/合同/转正强提醒** + **倒班班次预设**(白班/中班/晚班/夜班/护士早班),体现护理/餐饮岗位的强监管与24小时护理特性。

### 3.10 办公(OA协同中台)

- **交班管理**:结构化模板(房号/产妇宝宝数/喂养方式/出院诊断等)+自由文本,按班次留痕。
- **消息通知是全系统待办枢纽**:采购/入库/请假/报销/退款/优惠/客户资源分配等各模块的审批/待办事项统一推送到此,点击直达处理。
- **协同任务=客户服务节点SOP**:预设"入住前准备工作""离店前工作准备"等协同单模板(含多个子任务),客户到达节点自动生成协同任务实例,按部门认领/完成,确保多部门不遗漏。
- **流程审批引擎**(通用工作流核心):
  - 审批项目可自定义:名称/图标/审批层级(1~5级)/默认审批人/所属分类(行政类/财务类/人事类/考勤类/其他类)/**关联操作**(不关联/生成采购单/生成出库单/生成其他支出)/门店范围/启用状态。
  - 实测可发起的审批类型达20余种:请假单、报销申请、行政部请购单、物品申领、退款申请、产康项目退款、申请派单、申请赠送项目、日常签呈等。
  - 状态流:制单中→审批中(逐级)→通过/不通过;不通过3个月内可重新提交。
  - "已审支出"页跟踪审批通过后是否已生成正式支出单,形成**审批‑财务闭环**,是行政审批打通财务的关键设计。
- **场地/设备预定**:按4个时段(00-05/06-11/12-17/18-23)展示空闲/占用,场地涵盖SPA室/会议室/诊室,设备涵盖车辆/仪器。

### 3.11 商城(客户端小程序后台)

- 本质是把线下可售的护理/产康服务、月子餐点餐、实物母婴用品**统一搬到线上小程序**,供客户自助下单/核销。
- **订单三分类**:点餐类/商品类/服务类,状态流:待处理/未支付→处理中→已处理/已取消;支持批量打印交易单。
- **取件码核销**:线下自提场景专用,按点餐/服务/商品三类分别核销,可勾选"自动处理订单并完成项目"实现自动化核销。
- **优惠券三级体系**:优惠券类型(分类)→优惠券管理(规则模板,满减/满折+封顶,限量发放)→优惠券发放(定向发给客户,跟踪使用情况);支持优惠券"面值可转服务卡",打通商城与线下服务卡体系。
- **商品分级定价**:按会员等级(普通/白银/黄金/钻石)差异化定价 + 积分兑换,多门店各自独立上架维护商品。

### 3.12 知识库(内容与培训中枢)

- **对内**:目录管理→知识管理(文档,含视频/附件)→我要学习(员工自助学习)/学习记录(审计),配合试卷管理→在线考核(我的考试/考试批阅/考试查询,支持自动批阅或人工批阅)构成"学习+考核"闭环。
- **对外(微客宝)**:孕周知识(按孕周)、宝宝知识(按月龄)科普文案配置 + 活动配置(门店活动日历),是客户端内容运营与获客转化的内容供给端。
- 素材管理基于阿里云OSS统一托管视频/图片/文件,为知识文档与微客宝活动提供公共资源池。

### 3.13 系统(底层基础设施/治理中枢)

这是支撑其余全部业务模块的地基,建议**优先参考本模块设计**:

- **RBAC权限矩阵**:角色(如"超级管理员""电话销售员""门店销售员""护理人员")= 权限点集合 × 应用门店范围。权限矩阵横向覆盖约20个业务大类(客户/房间/护理/服务/财务/人事/统计/月嫂/商城/月子餐/库存/知识库/系统管理/共享股东/数据同步…),每个大类再拆"业务操作权限"与"基础设置权限"两栏,合计数百个功能点。**高风险操作标"‑危"(如删除客户、修改已出入库价格、线上退款),特权操作标"‑特"(如赠送项目、撤销已出库商品)**,授权时一目了然。
- **多门店/连锁架构**:集团(会宝云服,提供电子签/电子发票增值服务)→区域→门店→部门/职务/团队。门店详情页有十余个Tab(基本信息/门店职务/微客宝展示/开票设置/支付设置/导入数据/集采设置/门店参数/托管监控…),实现"总部统一框架+门店灵活定制"——尤其是微客宝小程序的十余项功能可逐店单独开关(启用服务销售/启用点餐/隐藏货币符号/禁止用会员余额支付等)。
- **系统参数(全局业务规则)**:客户最大透支金额(0/正数/负数三种语义)、标准月子入住天数、限制手机号跨门店重复、积分兑换现金比率等,是贯穿客户/财务/房间模块的全局规则源。
- **系统信息页证实SaaS订阅模式**:AppKey、版本号、服务时间(订阅有效期)、最大授权门店数/账户数/房间数、短信余额(按条计费)。
- **操作日志+系统日志双审计**:前者记录用户页面访问轨迹(含IP),后者记录与第三方(支付网关"收钱吧"等)交互的原始报文,分别服务合规审计与技术排障。
- **房间硬件标签**(标签管理):为每个房间生成二维码/NFC标签实例,支撑护理/房态模块的扫码交互——注意与"客户标签"(画像标签,属客户模块)是完全不同的概念,设计时需明确区分命名空间。

## 四、核心业务实体与数据模型建议

综合13个模块的字段与关联关系,建议"伴月轩"系统的核心实体至少包含以下几类,并注意其**多对多/一对多**关系:

| 实体域 | 核心实体 | 关键关系 |
|---|---|---|
| 组织架构 | 集团/区域/门店/部门/职务/团队/角色/账号 | 门店是几乎所有业务数据的顶层归属维度;角色×门店范围决定权限 |
| 客户主档 | 客户(妈妈)/宝宝(1:N,多胞胎)/亲属/推荐人 | 客户是全系统锚点,妈妈与宝宝需拆分为独立子档案但共享入住区间 |
| 销售/合同 | 线索/销售机会/合同(Word+网签两态)/签约套餐/续签套餐 | 线索→客户→销售机会→合同,状态机贯穿全周期 |
| 房态 | 房源/房型/楼层/预订/入住记录 | 客户与房间是 N:M 的时间区间关系(可换房、可重叠冲突检测) |
| 护理 | 护理字段(元数据)/护理项目(表单)/护理方案(模板)/护理记录/护理异常/档案 | 建议直接采用"字段元数据驱动表单"设计,避免每种护理表单硬编码 |
| 服务/商品 | 产品(服务/商品/点餐/膳品统一目录)/销售单/服务记录/服务包 | 产品可绑定"默认物料",核销时自动触发出库,建议保留这一联动设计 |
| 库存 | 商品/仓库/供应商/采购单/入库单/出库单/调拨单/盘点单 | 单据统一"制单→审批→执行→流水→月结"生命周期 |
| 财务 | 资金账户/会员账户/套餐账户/服务卡/代金卡/收款单/结算单 | 强烈建议采用"多资金池独立核算+统一资金账户确认"两层设计,避免不同用途资金混算 |
| 人事 | 员工/排班/业绩/提成/手工费/薪资单 | 双提成体系(业绩提成 vs 手工费)建议作为两条独立可扩展的核算链路 |
| 审批 | 审批项目(类型元数据)/审批单/审批人链 | 建议做成"类型可配置+关联操作可配置(自动生成下游单据)"的通用引擎,而非为每种审批单独开发 |
| 月嫂 | 月嫂档案/档期/派单/费用 | 可视为"特殊员工+订单撮合"的独立子域,与人事、客户均有连接 |
| 月子餐 | 膳食计划/用膳人/禁忌/菜品/食材 | 计划→个人绑定→当日汇总(菜品预算)→食材折算(与库存打通)三层设计值得直接复用 |

## 六、给"伴月轩"系统设计的建议

### 6.1 优先级建议(如需分期建设,以下按对业务闭环的必要性排序)

1. **P0 必须**:系统(RBAC+多门店)、客户(CRM+签约)、房间(房态+排房)、财务(收款+资金账户)—— 这四个模块构成"能签约、能入住、能收钱"的最小闭环,与README中"P0阶段"的规划一致。
2. **P1 核心业务**:护理(母婴档案+日常护理)、服务(产康/商品/点餐执行)、库存(采购入库出库)—— 覆盖核心服务交付。
3. **P2 效率与合规**:人事(排班+提成+薪资)、办公(审批引擎+协同任务)、月子餐(排餐+预算)。
4. **P3 增值与扩展**:月嫂(如无住家护理业务可暂不做)、商城(小程序电商)、知识库(培训)、统计(经营分析报表,建议在各业务模块数据积累后再统一建BI层)。

### 6.2 值得直接借鉴的设计模式

- **统一"服务单"模型**(服务/商品/点餐共用同一套预约‑执行‑核销框架)可大幅降低"服务""商城""月子餐"等模块的重复开发量,建议在架构设计阶段就抽象出这一层。
- **护理表单的"字段元数据→表单模板→方案组合"四层设计**,比为每种护理记录单独建表更具扩展性,强烈建议采用类似的低代码表单引擎思路。
- **审批引擎"类型可配置+关联操作可配置"**(审批通过后自动生成采购单/出库单/支出单)是打通行政、财务、库存流程的关键,建议作为独立的通用能力模块而非附属于各业务模块。
- **多资金池 + 统一资金账户确认**的财务模型,能清晰区分"客户预付款负债"与"公司实际银行存款",建议参考其"业务收付款→入账确认→资金账户余额→全量流水"四层架构。
- **门店级功能开关**(如微客宝十余项独立开关)让总部可以用同一套代码支撑不同业态子门店(月子中心/游泳馆/医美店等),如果"伴月轩"有多业态扩展规划,建议提前预留这一设计空间。

### 6.3 需要规避或谨慎处理的点

- 一月妈咪的"客户标签/用户画像"中出现"企业高管""明星""官员家属""军人家属"等敏感身份标签及"车辆型号""客户预算"等隐私字段,自建系统若涉及类似高端客群画像,**建议加严格的字段级权限控制与数据脱敏**,避免合规风险。
- 从截图观察,该系统测试/演示数据中存在不少"测试""111""AAA"等脏数据及个别字段命名不规范(如护理表单中出现疑似OCR识别错误的字段名),提示其字段扩展机制虽然灵活,但也容易在长期迭代中产生技术债,建议"伴月轩"在做可配置字段引擎时,给自定义字段增加命名规范校验与定期治理机制。
