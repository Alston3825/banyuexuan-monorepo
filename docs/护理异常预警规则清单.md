# 护理异常预警规则清单

> 用途：《软件项目开发计划》P2 交付物之一——"护理异常预警规则清单（为 P4 的 AI 护理助手预留数据结构）"。
> 本清单说明护理异常的**判定机制**与**数据来源**，不是一份写死的规则表——因为真正的判定阈值
> （体温正常范围、恶露正常选项等）由门店护理主管在"护理字段管理"页面动态维护，会随时间和门店
> 实际情况调整。P4 开发 AI 护理助手时应从下述数据结构实时读取规则，而不是把本文档里的示例值
> 硬编码进 Agent 逻辑。

## 1. 判定机制（单档判定，不做多级严重度）

护理记录提交时（`CareRecordService.create` → `detectAbnormalFields`），对表单模板挂载的每个
`CareFieldDefinition` 逐字段判断：

| 字段控件类型（`controlType`） | 正常值域字段 | 判定规则 |
|---|---|---|
| `NUMBER`（数值） | `normalMin` / `normalMax` | 提交值 < `normalMin`（若已设置）或 > `normalMax`（若已设置）即判定为异常；两者都为空则该字段不参与异常判定 |
| `SELECT` / `RADIO`（下拉/单选） | `normalOptionValues`（字符串数组） | 提交值不在 `normalOptionValues` 列表内即判定为异常；该字段为空/未配置则不参与判定 |
| `TEXT` / `TEXTAREA`（文本） | 无 | 不参与自动异常判定（文本内容需人工阅读） |

命中判定的字段会为**每个提交的护理记录**各自生成一条独立的 `CareAbnormality`（一条记录可能同时
触发多条异常，逐字段独立记录，互不覆盖）。异常记录携带 `fieldId`（触发字段）、`fieldValue`（触发时
的实际值）、`occurredAt`（护理记录的发生时间，不是提交时间）、`careRecordId`（可追溯回原始记录）。

本期**不做**多级严重度（如"轻度/中度/重度异常"），严重程度判断留给护理人员在异常的跟进记录
（`CareAbnormalityFollowUp`，复用 `FollowUpService`，`businessType='CARE_ABNORMALITY'`）里人工描述——
见 [业务规则确认记录.md](./业务规则确认记录.md) #7。

## 2. 异常记录的状态机

`CareAbnormality.status`：`OPEN`（自动生成，待处理）→ `FOLLOWING`（有跟进记录后自动推进）→
`RESOLVED` / `IGNORED`（护理人员手工处理，需填写 `resolveNote`，乐观锁 `version` 校验并发修改）。

## 3. 数据来源（P4 对接指引）

AI 护理助手需要判断"当前哪些字段配置了异常规则、规则内容是什么"时，应查询：

- `GET /api/v1/care/fields`（可加 `?targetType=MOTHER|BABY` 过滤）——返回全部 `CareFieldDefinition`，
  包含 `controlType`、`normalMin`、`normalMax`、`normalOptionValues`、`options`（候选项）、`unit`。
- 已生成的异常事实：`GET /api/v1/care/abnormalities`（可加 `motherProfileId`/`babyProfileId`/`status`
  过滤），每条记录都带 `field`（触发字段完整定义）与 `careRecord`（触发记录完整表单内容），足以让
  Agent 还原"当时提交了什么、为什么被判定异常、正常范围是什么"。

不要假设字段编码（`code`）在不同租户/门店间固定——本系统按租户维护字段字典，字段的存在性与阈值
均以数据库当前配置为准。

## 4. 当前示例配置（仅供理解格式，非生产规则）

开发/测试环境里通过端到端测试创建过的示例字段（`apps/api/test/p2-care-flow.e2e-spec.ts`）：

| 字段 | 适用对象 | 控件类型 | 正常值域示例 |
|---|---|---|---|
| 体温 | 妈妈 | NUMBER | 36 ~ 37.5 ℃ |
| 恶露情况 | 妈妈 | SELECT | 仅 `normal`（正常）为正常值，`abnormal_odor`（异味）等其他选项均触发异常 |

生产环境的真实规则（如喂奶量、体重变化等）需要门店护理主管在"护理字段管理"页面逐项录入，
目前系统尚未预置任何生产用护理字段。
