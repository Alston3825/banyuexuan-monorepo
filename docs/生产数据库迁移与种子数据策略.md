# 生产数据库迁移与种子数据策略

## 一、结构变更：用 `prisma migrate deploy`，不用 `prisma db push`

开发环境这些年一直用 `prisma migrate dev` 生成迁移文件（`apps/api/prisma/migrations/`目录下几十个文件夹）。生产环境**只应用已经生成好的迁移文件**，不重新生成、不做交互式确认：

```bash
cd apps/api
npx prisma migrate deploy
```

这条命令是幂等的——按顺序应用所有还没在生产库执行过的迁移，已执行过的自动跳过，可以放心在每次发布时都跑一遍，不用担心重复执行。`apps/api/Dockerfile`里已经把这一步写进了容器启动命令（`CMD`），所以正常走 `docker compose up` 部署时会自动执行，不需要你手动跑。

**绝对不要**在生产库上用 `prisma db push`——这条命令是给开发阶段快速试错设计的，会跳过迁移历史文件，且在字段类型变更/删除字段时可能不经确认直接丢数据。

## 二、种子数据：结构性配置 vs 示例业务数据

`apps/api/prisma/seed.ts`这个文件本来只是本地开发用的演示数据脚本，本轮改造后区分了两类内容：

**结构性配置**（任何环境都需要，生产环境也不例外）：
- RBAC四级权限目录（381个权限点，模块/页面/按钮/字段）
- 角色定义（超级管理员/店长）及其权限授予关系
- 工作流定义（合同签约审批、退款审批、库存单据审批等7种审批流程的骨架）
- 系统参数（密码策略、token有效期等）

这些是应用运行必需的底层配置，不是"演示数据"——如果生产库里没有这些，登录、审批、权限判断这些基础功能都无法运作。

**示例业务数据**（只有开发/预发环境需要）：
- 第二个演示账号 `store_manager`
- 示例客户"李女士"、示例线索、示例合同、示例预订、示例收款记录

这些是纯粹为了本地联调/演示方便造的假数据，生产环境不应该有虚构的客户信息。

## 三、生产环境首次上线怎么跑种子脚本

```bash
cd apps/api
NODE_ENV=production \
SEED_TENANT_CODE=<你的真实租户代码，比如公司英文缩写> \
SEED_TENANT_NAME=<真实租户名，比如"伴月轩月子中心"> \
SEED_STORE_CODE=<第一家门店代码> \
SEED_STORE_NAME=<第一家门店真实名称> \
SEED_ADMIN_USERNAME=<你要用的管理员登录名> \
SEED_ADMIN_PASSWORD=<强密码，用 `openssl rand -base64 16` 生成一个> \
npx prisma db seed
```

这条命令跑完之后会产出：全部381个权限点、超管/店长两个角色定义、全部工作流审批流程骨架、系统参数，以及**恰好一个**你指定用户名密码的超级管理员账号——不会有 `store_manager` 演示账号，也不会有任何虚构客户/合同数据。

**六个环境变量缺一个都不行**：脚本顶部有校验，`NODE_ENV=production`但缺少任一变量会直接报错拒绝执行，且密码长度不足12位或等于开发默认密码也会拒绝——这是刻意设计的安全阀，防止手滑用开发环境的默认账号密码跑生产库。

跑完之后，用这个超管账号登录系统，后续所有真实门店、真实员工账号、真实店长账号都通过后台管理界面手动创建，不再需要改seed脚本。

## 四、后续新增门店/新增权限点怎么办

- **新增门店**：不需要跑seed脚本，直接在系统后台"门店管理"里新建即可（这是常规业务操作，走的是应用本身的CRUD接口，不是种子脚本的职责）。
- **新增权限点**（比如新开发了一个模块）：这类改动是代码改动的一部分，`seed.ts`里的权限点目录会同步更新，正常发布新版本代码后重新跑一次`npx prisma db seed`即可把新增的权限点补进生产库（`upsert`语义，不会影响已有数据），不需要重新走一遍完整的"首次上线"流程（即不需要重新设置六个环境变量，`SEED_TENANT_CODE`等变量此时不需要重新提供新值——但由于脚本顶部对production环境校验这六个变量必须存在，重新运行时仍需要把这六个变量重新传入，值保持和首次上线时一致即可，upsert会识别到租户/门店已存在从而跳过创建，只补权限点/工作流定义里新增的部分）。
