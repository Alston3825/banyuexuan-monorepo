# 集成规范：伴月轩智能呼叫定位系统 ⇄ 伴月轩月子中心管理系统

> 对应《伴月轩智能呼叫定位系统 — 软件开发规划文档》第 15 章。**管理系统是基础数据的唯一来源**；呼叫系统只读拉取、写回呼叫记录，双方互不读对方数据库。
> 机器可读的接口都在 `/api/v1/integration/v1/*`（需 API Key）。API Key 在管理系统「系统管理 → 系统集成（呼叫定位）」里生成。

## 1. 全局 ID 规则（两个系统统一用这一套）

| 呼叫系统字段 | 管理系统来源 | 格式 | 说明 |
|---|---|---|---|
| `store_id` | `Store.id` | cuid 字符串（如 `cm3x…`，25 位左右） | 全局唯一、不连号；另有人看的 `store_code`（如 ST001） |
| `room_id` | `Room.id` | cuid | 另有 `room_no`（房号，如 8801）、`floor`（楼层标签，如 `2F`/`B1`，**不是纯数字**） |
| `staff_id` | `Account.id` | cuid | 另有 `employee_no`（工号，人看的）。**手表/账号校验返回的都是它** |
| `stay_id` | `RoomOccupancy.id` | cuid | 一次入住（预订→在住→离店）。另有人看的 `stay_no`（占房单号） |
| `customer_id` | `Customer.id` | cuid | 另有 `customer_no`；宝妈称呼见 `salutation` |
| `baby_id` | `BabyProfile.id` | cuid | |
| `service_code` | `ServiceCatalogItem.serviceCode` | 大写下划线，如 `NEED_NURSE` | 默认：NEED_NURSE/BABY_CRY/MILK_STORAGE/HOT_WATER/CLEANING/EMERGENCY/CUSTOM，可在后台增删 |
| `watch_id` | `EmployeeProfile.watchId` | 呼叫系统里的手表设备号 | 同租户唯一 |
| `tablet_device_id` / `beacon_ids` | `RoomDeviceBinding.deviceCode` | 呼叫系统里的设备号 | 一间房 1 台平板 + 多个信标；**信标编号格式固定为「大号-小号」（如 1601-1），与手表上报一致，系统会校验**；同一设备号不能绑两间房 |
| `call_id` | 呼叫系统自己生成 | 建议 UUID | 管理系统按 `(系统代号, call_id)` 幂等保存 |

规则：① 所有主键都是 cuid（非自增、全局唯一），**跨店不会撞号**，呼叫系统不需要再加前缀；② 呼叫系统里的 `store_id/room_id/staff_id/stay_id` 一律存管理系统给的原值，不要自己造；③ 人看的编号（房号、工号、客户号）只用于显示，不当主键。

## 2. 认证

`Authorization: Bearer bmx_xxxxxxxx`（或 `X-Api-Key`）。Key 绑定租户，可限定只能访问某一家门店；可随时停用/重置（旧 Key 立即失效）。Key 明文只在生成时显示一次，库里只存哈希。

## 3. 只读主数据（增量拉取）

所有列表接口支持 `updatedSince=<ISO时间>`（只取该时间之后变更的），返回：
```json
{ "items": [...], "count": 12, "hasMore": false, "nextSince": "2026-11-10T08:00:00.123Z", "serverTime": "..." }
```
`hasMore=true` 时，用 `nextSince` 作为下一次的 `updatedSince` 继续拉（每页最多 500）。首次不带 `updatedSince` = 全量。建议：启动全量一次 + 每 30–60 秒增量 + 收到 MQTT/事件时立即增量。可选 `storeId` 过滤。

### 3.1 `GET /integration/v1/stores`
```json
{ "store_id": "cm…", "store_code": "ST001", "name": "高新店", "address": "…", "status": "ACTIVE", "updated_at": "…" }
```
### 3.2 `GET /integration/v1/rooms?storeId=`（楼层+房间+设备绑定）
```json
{ "room_id": "cm…", "store_id": "cm…", "floor": "2F", "room_no": "2801", "room_type": "DELUXE", "room_type_name": "豪华房",
  "status": "OCCUPIED", "current_stay_id": "cm…", "tablet_device_id": "PAD-0001", "beacon_ids": ["2801-1","2801-2"], "updated_at": "…" }
```
`status`：`FREE / OCCUPIED / PENDING_CLEANING / MAINTENANCE`。
### 3.3 `GET /integration/v1/staff?storeId=`（仅在职启用账号）
```json
{ "staff_id": "cm…", "store_id": "cm…", "name": "王护士", "phone": "138…", "employee_no": "1023", "roles": ["NURSE"],
  "watch_id": "W-007", "duty_status": "ON_DUTY", "responsible_floors": ["2F","3F"], "employed": true, "updated_at": "…" }
```
`duty_status`：`ON_DUTY 在岗 / OFF_DUTY 离岗 / RESTING 休息`（呼叫系统只派给 ON_DUTY）。
### 3.4 `GET /integration/v1/stays?storeId=&status=CHECKED_IN,RESERVED`
```json
{ "stay_id": "cm…", "stay_no": "OC2026…", "store_id": "cm…", "room_id": "cm…", "room_no": "2801", "floor": "2F",
  "customer_id": "cm…", "customer_no": "C…", "mother_name": "李小雨", "salutation": "小雨妈妈",
  "babies": [{ "baby_id": "cm…", "name": "豆豆", "gender": "MALE", "birth_date": "2026-10-20T00:00:00.000Z" }],
  "status": "CHECKED_IN", "planned_check_in": "…", "planned_check_out": "…", "actual_check_in_at": "…", "actual_check_out_at": null, "updated_at": "…" }
```
`status`：`RESERVED 已预订 / CHECKED_IN 在住 / CHECKED_OUT 已离店 / CANCELLED 已取消`。**日期都是预估**（行业惯例），以 `actual_*` 为准；房间以办理入住时现场安排为准，所以用 `stay` 当前的 `room_id`，别用预订时的。
### 3.5 `GET /integration/v1/service-codes`
```json
{ "service_code": "NEED_NURSE", "name": "呼叫护理师", "category": "CALL" }
```

## 4. 管理系统事件（拉取，可再转发 MQTT）

`GET /integration/v1/events?storeId=&afterSeq=<上次拿到的nextSeq>` → `{ items:[{event_id, seq, store_id, type, topic, entity_id, payload, timestamp}], nextSeq, hasMore }`

`topic` 即规划文档约定的 `{store_id}/mgmt/{event_type}`，将来接 MQTT 时按此转发即可。现有事件：

| type | 触发 | payload 关键字段 |
|---|---|---|
| `stay.checked_in` | 办理入住（含现场换房） | stay_id, room_id, customer_id, 计划/实际时间 |
| `stay.checked_out` | 办理离店（含逾期补办离店） | 同上 |
| `stay.room_changed` | 预订阶段换房 | 同上 |
| `staff.duty_changed` | 员工当班状态/手表/负责楼层变动 | staff_id, duty_status, watch_id, responsible_floors |

事件只是“提醒你去拉”：收到后用 3.x 的增量接口取最新数据即可，**不要只靠事件**（断线补偿用 `afterSeq`）。

## 5. 呼叫系统写回

### 5.1 `POST /integration/v1/call-events`（幂等）
同一 `call_id` 重复发 = 更新同一条；已有的时间/处理人不会被空值覆盖，所以可以随流程分多次发（创建→派单→接单→完成）。
```json
{ "call_id": "uuid", "store_id": "cm…", "room_id": "cm…", "stay_id": "cm…",
  "request_type": "CALL_REQUEST", "service_code": "NEED_NURSE", "status": "COMPLETED",
  "initiated_at": "…", "dispatched_at": "…", "accepted_at": "…", "completed_at": "…",
  "handler_staff_id": "cm…", "feedback": "宝妈满意", "payload": {} }
```
校验：`room_id`、`stay_id` 必须属于该 `store_id`，否则 400（防串店）。管理系统「呼叫记录」后续可按 `stay_id` 汇入客户服务记录。

### 5.2 `POST /integration/v1/auth/verify`（统一账号校验）
请求 `{ "username": "手机号或用户名", "password": "…" }` → 成功 `{ valid:true, staff_id, store_id, name, roles:[…], permissions:[…] }`；失败 `{ valid:false }`（HTTP 200，不泄露具体原因）。若 Key 限定了门店，别店账号一律 `valid:false`。

### 5.3 `GET /integration/v1/ping` 探活
返回 `{ ok:true, system, serverTime }`。

## 6. 管理系统里谁来维护这些数据

- **房间平板/信标绑定**：「系统管理 → 系统集成 → 房间设备绑定」（店长可维护本店）。
- **手表设备号 / 当班状态 / 负责楼层**：「员工档案 → 编辑 → 呼叫定位系统」。
- **宝妈称呼**：客户编辑页「宝妈称呼」。
- **服务项（呼叫按钮）**：系统集成 → 服务项字典。
- **接入系统 + API Key**：系统集成 → 接入系统（仅总部/管理员）。

## 7. 作为独立产品卖给其他月子中心时

呼叫系统只依赖上面 5 类数据 + 事件 + 校验 3 个接口。对方没有伴月轩管理系统时，实现一个同样接口的“适配器”（或用 CSV 导入）即可，呼叫系统内部不要出现管理系统库表名。
